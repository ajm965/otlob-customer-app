# Otlob Customer App — Platform Readiness Report

## 1. Flutter and Dart SDK

- Flutter: `3.38.5`, stable channel
- Dart: `3.10.4`, stable
- Xcode: `26.6`
- CocoaPods: `1.16.2`

## 2. Android Platform Status

The standard Android runner was generated by:

```text
flutter create --platforms=android,ios --org=com.example \
  --project-name=otlob_customer_app .
```

The Android project uses the versions supplied by the installed Flutter SDK:
`flutter.compileSdkVersion`, `flutter.minSdkVersion`,
`flutter.targetSdkVersion`, and `flutter.ndkVersion`. It uses the generated
Kotlin DSL Gradle structure and Java 17 configuration. No Gradle, Kotlin, SDK,
or dependency version was manually changed.

Flutter recognizes the generated Android project. However, this workstation
does not have an Android SDK configured, so a local APK build is blocked until
the Android SDK is installed and Flutter is configured to find it.

## 3. iOS Platform Status

The standard iOS runner was generated by the same Flutter command. Xcode and
CocoaPods are available on this workstation. The following development build
succeeded without code signing:

```text
flutter build ios --debug --no-codesign --dart-define=APP_ENV=development
```

No physical device, signing certificate, provisioning profile, or release
archive was required.

## 4. Application Identifier Status

The generated identifiers are deliberately non-production placeholders:

- Android application ID and namespace:
  `com.example.otlob_customer_app`
  in `android/app/build.gradle.kts`
- iOS bundle identifier:
  `com.example.otlobCustomerApp`
  in `ios/Runner.xcodeproj/project.pbxproj`

Before release, replace both with the legally approved organization identifier,
rename the Android Kotlin package path if needed, and update the iOS test
bundle identifier consistently. Do not publish with `com.example`.

## 5. Environment Status

The C3 environment foundation remains unchanged:

- `development`
- `staging`
- `production`

It uses `--dart-define=APP_ENV=...`, defaults to development, and accepts
injected `EnvironmentConfig` in tests. The successful iOS debug build was
performed with `APP_ENV=development`. No URLs, API keys, Firebase values,
credentials, or other secrets were added.

## 6. Localization Status

Arabic remains the primary application locale and resolves to RTL through
Flutter localization delegates. English remains LTR. The existing minimal
bootstrap localization delegate and RTL/LTR widget tests are unchanged.

The previous comment-only `l10n.yaml` placeholder was removed because Flutter
treats any `l10n.yaml` as a localization-generator configuration; the
non-mapping placeholder caused native builds to fail. Localization remains
manual and minimal until an approved ARB catalog is introduced.

No images, icons, fonts, animations, or feature assets were added.

## 11. Known Limitations

- Android local builds cannot run on this workstation until the Android SDK is
  installed and configured (`ANDROID_HOME` or `flutter config --android-sdk`).
- iOS debug build was intentionally unsigned. Signing and App Store
  distribution are not configured.
- Application display names, app icons, launch visuals, platform flavors, and
  production identifiers are still generated placeholders.

## 12. Required Actions Before Production Release

1. Obtain and apply the approved organization identifier to Android and iOS.
2. Install and configure the Android SDK on developer and CI machines.
3. Set up managed Android and iOS release signing outside source control.
4. Establish platform-specific development, staging, and production build
   flavors only after their requirements are approved.
5. Replace generated icons, launch visuals, and display metadata with approved
   Otlob assets.
6. Add approved localization catalogs, legal metadata, privacy disclosures,
   backend integrations, and release compliance checks in their dedicated
   future sprints.
